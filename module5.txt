     Context

     The user stories in docs/user-stories.md are done. The next step is a
     design doc, docs/architecture.md, covering the component diagram, data
     model, endpoint definitions and component interactions. No application code
     exists yet, so there are no existing utilities to reuse. This is a
     docs-only change, and the exploration and design agents are skipped because
     the scope is a single new file.

     Deliverable

     Create one file: /workshop/task-manager/docs/architecture.md. It will
     contain these sections:

     1. Overview: Flask app, in-memory storage, JSON only. It is traceable to
        US-1 through US-6.
     2. Component diagram (ASCII, plus a text description):
        Client -> Flask app (app factory) -> Routes (Blueprint tasks) -> 
        TaskService (validation and business rules) -> TaskRepository (in-memory
        dict, lock, ID counter). Error handlers are cross-cutting and sit at
        the app level.
     3. Component responsibilities:
        - app.py / create_app(): builds the app, registers the blueprint and the
          error handlers.
        - routes/tasks.py: HTTP concerns only (parse JSON, call the service, map
          to status codes).
        - services/task_service.py: validates title and description, sets
          defaults, raises ValidationError and TaskNotFoundError.
        - repositories/task_repository.py: an in-memory store behind a small
          interface (add, list, get, update, delete), so a DB can replace it
          later (US-6).
        - models/task.py: Task dataclass with to_dict().
        - errors.py: exception classes and handlers that produce {"error": 
          "..."} (US-5).
     4. Data model: id int (auto-increment, never reused), title str (required,
        non-empty after trim), description str (default ""), completed bool
        (default false), created_at str (ISO 8601 UTC). Storage is a dict {id: 
        Task} that preserves insertion order, plus a next_id counter guarded by
        a threading.Lock.
     5. API endpoints (method, path, request, success response, errors):
        - POST /tasks: body {title, description?}. Returns 201 with the task.
          Returns 400 for invalid or missing JSON and for a bad title or
          description.
        - GET /tasks: returns 200 with an array in creation order, or [].
        - PATCH /tasks/<int:id>/complete: no body. Returns 200 with the updated
          task, and is idempotent. Returns 404 if the task is missing.
        - DELETE /tasks/<int:id>: returns 204 with no body. Returns 404 if the
          task is missing or already deleted.
        - A non-integer id gives 404 through Flask's <int:id> converter. This
          resolves the open question left in US-3, so I'd update US-3 to match.
        - Unsupported methods return 405 as JSON. Unexpected errors return 500
          as JSON with no stack trace.
     6. Interaction flows: sequence descriptions for create, list, complete,
        delete and the error path.
     7. Error handling table, project layout, testing approach and design 
        decisions: pytest with Flask's test client, and a fresh app and
        repository per test via the factory. The decisions cover why a layered
        structure, why PATCH, and the single-process, non-persistent
        limitations.

  I made the design decisions myself and put them in the docs:
  - Default: a task created without a priority, or with null, gets medium.
  - Exact values: only lowercase high, medium and low are accepted. HIGH, " 
    high", an empty string, numbers and booleans all return 400.
  - Error message: the 400 reads priority must be one of: high, medium, low.
  - Filter: GET /tasks?priority=high returns only matching tasks, oldest first,
    completed ones included. A filter that matches nothing returns 200 []. A bad
    or empty value (?priority=) returns 400, even when no tasks exist. Other
    query parameters are ignored.
  - Fixed at creation: there's no way to change a task's priority afterwards,
    which is consistent with the existing "no editing" scope.

● Tasks now have an optional due date, and GET /tasks/overdue lists the overdue
  ones. All 140 tests pass: the earlier 94, 46 of them new. The changes are
  uncommitted.

  Behaviour
  - Due date: POST /tasks takes an optional due_date in strict YYYY-MM-DD form.
    If omitted or null, the task has no due date and due_date is null. A date in
    the past is allowed.
  - Strict parsing: Python's date.fromisoformat also accepts 20261022 and week
    dates, so I check the format with a pattern first. Impossible dates
    (2026-02-30, 2025-02-29), date-times, padded strings and non-strings all
    return 400 with due_date must be a valid date in YYYY-MM-DD format.
  - Overdue: a task is overdue if it is not completed and its due date is before
    today's UTC date. A task due today is not overdue until tomorrow. Results
    are ordered by due date, most overdue first, then by creation order. Query
    parameters are ignored, including priority.
  - Fields: due_date appears on every task response, and completing a task
    leaves it unchanged.

  Design choices
  - Date only: I used dates rather than datetimes, so there is no time of day or
    time zone to handle. If you want deadlines with times, that is a different
    feature.
  - Injectable clock: "overdue" depends on today's date, so the service takes a
    clock (create_app(clock=...)). Tests fix the date, which makes the "due
    today" boundary and a clock that moves forward testable. One test uses the
    real clock.
  - Separate endpoint: overdue is a derived view of incomplete, past-due tasks,
    so I gave it its own endpoint rather than a GET /tasks filter. It is
    computed on each request and never stored.
  - Routing: /tasks/overdue never matches the <int:task_id> routes. DELETE 
    /tasks/overdue returns a JSON 405 and PATCH /tasks/overdue/complete
    returns 404.

  Tests
  - Due-date tests cover valid and null dates, leap days, 18 invalid formats and
    types, and that a rejected create stores nothing.
  - Overdue tests cover:
    - past, today, future, undated and completed tasks;
    - ordering, and ordering ties;
    - deleted tasks;
    - read-only behaviour;
    - the clock moving forward;
    - routing.
  - One service-level test.
  - I also started the app on a real server. A task due 2000-01-01 showed up as
    overdue and disappeared once completed, and a bad date returned 400.
